# BentoPDF Native on Linux (M4 packaging)

Unofficial packaging of BentoPDF as a locked-down Electron app. Linux x64
only here; macOS/Windows are CI-only later (NOT VERIFIED, nothing built).
Design and security model: [desktop.md](desktop.md). Roadmap gates:
[ROADMAP.md](ROADMAP.md#m4-entry-criteria-do-not-start-packaging-before-these-have-an-answer).

## Prerequisites (build)

- Node.js 22, npm, git, curl, `rpmbuild` (only for the `.rpm`; without it
  `scripts/package-linux.sh` builds AppImage and deb and says so).
- Network for the first build (npm, upstream clone, electron-builder tools).
- `desktop/` dependencies: `cd desktop && npm ci` (Electron 45.1.0,
  electron-builder 26.18.0, `@electron/fuses` 2.1.3, all pinned exactly).
- Immutable hosts (Bazzite/Silverblue): everything above runs in `$HOME`;
  nothing is layered. electron-builder's bundled `fpm` needs `libcrypt.so.1`
  (Fedora package `libxcrypt-compat`). If it is missing the deb/rpm step fails
  with `ruby: error while loading shared libraries: libcrypt.so.1`. Without
  layering: `dnf download libxcrypt-compat`, unpack it with `rpm2cpio | cpio -idm`
  and run the build with `LD_LIBRARY_PATH=<dir>/usr/lib64`. Ubuntu CI has it.

## Build

```sh
scripts/package-linux.sh          # builds dist/ if missing, then AppImage + deb + rpm into desktop/release/
packaging/verify-artifact.sh desktop/release/<artifact>   # release gate, one run per artifact (add --release for a release build)
packaging/verify-artifact.sh packaging/flatpak/.build/app   # the same gate on the Flatpak build tree
packaging/test-verify-artifact.sh   # mutation test of the gate itself (see Gate integrity)
cd desktop && npm run test:fuses -- release/linux-unpacked/bentopdf-native
cd desktop && npm run test:packaged -- release/<file>.AppImage   # headless smoke test of a disposable extracted COPY (AppImage only), never opens a window
packaging/flatpak/build-flatpak.sh   # Flatpak bundle, user scope (see Flatpak below)
```

`npm run dist:linux` in `desktop/` calls the same script. SOURCE.txt is
generated by `packaging/gen-source-txt.sh` before packaging.

## Install

| Format | How | Notes |
|---|---|---|
| AppImage | `chmod +x bentopdf-native-*.AppImage && ./bentopdf-native-*.AppImage` | no root; needs FUSE 2 and unprivileged user namespaces (below) |
| Flatpak | see "Flatpak install sequence" | the right choice on immutable hosts (Bazzite, Silverblue, Kinoite) |
| deb | `sudo apt install ./bentopdf-native-*.deb` | installs to `/opt/BentoPDF Native`; the post-install script picks the sandbox mode (see Sandbox) |
| rpm | `sudo dnf install ./bentopdf-native-*.rpm` | same layout. On Bazzite/Silverblue this needs layering (`rpm-ostree install`, then a reboot): **not recommended**, use the Flatpak or `--appimage-extract-and-run` |

There is **no auto-update**, deliberately: the app makes no network requests.
Install a newer package yourself. Nothing is signed (no keys exist in this
project); verify with the `SHA256SUMS` published next to a release.

### Immutable hosts (Bazzite, Silverblue, Kinoite): what to use

The sane options, in order: (1) the Flatpak; (2) the AppImage, run with
`--appimage-extract-and-run` if it will not mount. Do **not** layer the deb/rpm
just to get this application: layering changes the base image, needs a reboot
and ties it to image updates.

### AppImage: FUSE 2

An AppImage mounts itself with FUSE 2 (`libfuse2` / `fuse-libs`). If it is
missing, running the file prints `dlopen(): error loading libfuse.so.2` and
`AppImages require FUSE to run`, and nothing starts. Install `libfuse2`
(Debian/Ubuntu, package `libfuse2t64` on 24.04) or `fuse-libs` (Fedora; present on Bazzite), **or**
skip FUSE entirely:

```sh
./bentopdf-native-*.AppImage --appimage-extract-and-run
```

This unpacks to a temporary directory on every start (slower; the bundle is ~370 MB).
`./x.AppImage --appimage-extract` unpacks once into `squashfs-root/`, whose `AppRun` you can run directly.

### User namespaces (AppImage and Flatpak-less setups)

Chromium's sandbox needs unprivileged user namespaces. Check as your normal user:
`unshare --user true && echo works`, and read
`sysctl user.max_user_namespaces kernel.unprivileged_userns_clone kernel.apparmor_restrict_unprivileged_userns`
(a missing key is fine; `0`, `0` and `1` respectively mean "blocked"). When blocked,
the AppImage refuses to start and says so (see Sandbox); it never falls back to `--no-sandbox`.

### Flatpak install sequence

User scope, nothing needs root. Add flathub once, install the runtime and the
Electron base the app was built against, then the bundle:

```sh
flatpak remote-add --user --if-not-exists flathub https://dl.flathub.org/repo/flathub.flatpakrepo
flatpak install --user flathub org.freedesktop.Platform//25.08 org.electronjs.Electron2.BaseApp//25.08
flatpak install --user --bundle bentopdf-native-0.1.0.flatpak
flatpak run io.github.bearyjd.BentoPDFNative
```

The bundle contains the application plus the BaseApp's files (zypak and a few
libraries, with their licence texts); the runtime is not in the bundle. Building the
Flatpak itself additionally needs `org.freedesktop.Sdk//25.08`.

## Bundle layout decision: WASM payload outside the asar

`app.asar` holds only the shell (`package.json` + `src/`): 48,435 bytes. The
offline bundle (`dist/`, 4,394 files, 368 MB) is an `extraResource` at
`resources/dist/`, byte-for-byte the same file list as `dist/` (checked with
`diff` of both file lists on the built `linux-unpacked`).

Why not inside the asar:

- The static server (`src/static-files.js`) answers HTTP `Range` requests by
  reading file offsets. On plain files that is a plain seek and read; inside an
  asar the reads would go through Electron's patched `fs` over one 368 MB
  archive (not measured here; the choice is conservative, not benchmarked).
- Size: a 368 MB asar would make the code archive 7,500 times larger for no benefit.
- `OnlyLoadAppFromAsar` only restricts where *app code* (JS) is loaded from,
  so the payload outside the asar is not code the runtime will execute from
  there: it is served as data over `bento://app`.

Evidence in the artifact: `packaging/verify-artifact.sh` asserts
`resources/dist/index.html` exists, `app.asar` is < 5 MB, and the headless
smoke test loads `bento://app/index.html` from an extracted copy of the AppImage with
`BENTO_DIST=/nonexistent` set.

`BENTO_DIST` / `BENTO_TRANSPORT` resolve to `process.resourcesPath/dist` and
`scheme` when packaged; the environment overrides are not read at all when
`app.isPackaged` (`src/main.js`). Proof is dynamic (smoke test launches the
extracted AppImage copy, not the Flatpak any more (see "Packaged test mode"), with `BENTO_DIST=/nonexistent BENTO_TRANSPORT=carrier-pigeon`: it
still starts on `bento://app`; unpackaged, the same value exits with code 2) and
static (the gate greps the extracted `main.js` for the guard and rejects any
other `process.env` read).

## Electron fuses

Set by `desktop/tools/after-pack.js` (afterPack hook) from the single list in
`desktop/tools/fuse-config.js`: RunAsNode off, EnableNodeOptionsEnvironmentVariable
off, EnableNodeCliInspectArguments off, EnableEmbeddedAsarIntegrityValidation
on, OnlyLoadAppFromAsar on, EnableCookieEncryption on,
GrantFileProtocolExtraPrivileges off. `npm run test:fuses -- <binary>` reads the
fuse wire from a built binary and exits non-zero on any mismatch (7 of 7 pass on
the unpacked build and on the binary inside AppImage, deb and rpm via
`verify-artifact.sh`).

Honest limits: **nothing here relies on `EnableEmbeddedAsarIntegrityValidation`.**
Electron documents that fuse for macOS and Windows; on Linux it is believed to
do nothing, and the packaged app starting with it on proves nothing either way
(NOT VERIFIED that Electron 45 checks a digest on Linux). It is left on because
it is harmless, and `check-fuses.js` still requires it so the list cannot drift,
but it is not part of the security argument. The fuses that matter on Linux are
RunAsNode, NODE_OPTIONS, inspect arguments, OnlyLoadAppFromAsar and cookie
encryption. The remote-debugging port is a Chromium switch, not a Node one, so
it exists in every Electron app; `src/argv-policy.js` refuses it (below).

## Launch arguments and environment

`src/argv-policy.js` is an **allowlist**, applied to the first launch's `process.argv`
(exit code 2, logged) and to every second-instance `argv` (the whole invocation is dropped,
logged). Any argument that starts with a dash is a switch and is refused unless it is exactly
`--ozone-platform-hint=auto|wayland|x11`. This is an allowlist because a denylist is bypassable:
on POSIX Chromium also honours a **single** dash. Measured on the unpackaged app with Electron
45.1.0, headless: `-remote-debugging-port=0` opened a DevTools port (`DevToolsActivePort` written,
"DevTools listening" printed) and `-no-sandbox` was reported by `app.commandLine.hasSwitch`, exactly
like their double-dash forms. Matching is case-sensitive and exact, so `-no-sandbox`, `--NO-SANDBOX`,
`--no-zygote`, `--renderer-cmd-prefix`, `--browser-subprocess-path`, `--user-data-dir`,
`--proxy-server`, `--allow-file-access-from-files`, `--enable-features=`/`--disable-features=`,
`--disable-blink-features` and the rest are all refused (unit-tested). A bare `--` ends the options:
what follows is a file argument and still goes through the open-with validation. Only when
`BENTO_TEST_HEADLESS=1` is in the environment **and** (for a packaged build) the test-mode marker exists
(next section) are `--ozone-platform=headless`, `--remote-debugging-port=<n>`,
`--remote-debugging-pipe` and `--user-data-dir=<dir>` also accepted; that is how the test harnesses drive
Electron. The AppRun and Flatpak launcher unset `BENTO_TEST_HEADLESS`, `BENTO_DIST` and `BENTO_TRANSPORT`
for every normal launch.

### Packaged test mode (marker file)

PR #8 made packaged builds ignore `BENTO_TEST_HEADLESS`, which broke the packaged smoke test. It now
works like this: a packaged build honours test mode only if **both** the environment variable is `1`
**and** `<process.resourcesPath>/.bento-test-mode` passes `hasTestMarker` (`src/test-mode.js`): the
resources path is its own real path (no symlinked directory), the marker opens with `O_NOFOLLOW` (a
symlink fails), `fstat` on that descriptor says regular file, exactly one hard link, owned by the current
user, not group/world-writable, exactly 19 bytes, and the content is exactly `bento-test-mode-v1\n`.
Anything else, including any error, means "not test mode". **Issue #13:** this marker gate is a tripwire, not a boundary, and the test-mode code ships in every build; it must be compiled out of release builds before ANY signed release. Unit tests cover each check alone (a fake `fs`
isolates `isFile`, `nlink`, owner, mode and size, which real files cannot) and were mutation-checked.
`size` and `isFile` are not equivalent mutants once the fake `fs` is used; against a real filesystem the
content comparison and the file type already reject what they would reject.

`test/packaged-smoke.js` copies the AppImage into its own temp directory (the release artifact is never
modified, not even chmod), extracts the copy, creates the marker **in that extraction only**, runs the
extracted binary directly with the env, and removes the directory in a `finally` (also when extraction
fails). The app it launches gets `HOME` and `XDG_CONFIG_HOME/CACHE_HOME/DATA_HOME/RUNTIME_DIR` inside that
directory and never inherits `ELECTRON_DISABLE_SANDBOX` / `CHROME_DEVEL_SANDBOX` from the runner. Two
controls run on the same copy: (1) without the marker the binary refuses the debug port (exit 2 **and**
the "unsafe switch" message on stderr, so a different exit-2 reason cannot satisfy it); (2) with the marker
but started through the extracted `AppRun`, the launcher scrubs the env and the same exit-2 plus message
is required. Refusal-check children start as process-group leaders and the whole group is killed on
timeout and in `finally`.

What the release gate (`packaging/verify-artifact.sh`) now proves about the marker, from the packaged
`app.asar` itself: no `.bento-test-mode` anywhere in the artifact; `test-mode.js` still spells out every
control above (text check); the packaged `test-mode.js` and `argv-policy.js` are **run** by
`desktop/tools/check-asar-policy.js` (valid marker accepted; hard link, foreign owner, group/world-writable,
symlink, directory, symlinked resources path, wrong or near-miss token all refused; a packaged build with
the env but no marker, or with a truthy non-`true` marker, still refuses `--remote-debugging-port`); and
`main.js` passes `app.isPackaged && hasTestMarker(process.resourcesPath)` to the policy.
`packaging/test-verify-artifact.sh` mutates each of these (marker function returns true, each check removed,
argv-policy condition dropped or loosened, `main.js` passing a constant) and requires the gate to fail
**with the expected message**, so a case cannot pass for the wrong reason.

`process.env` reads are found by parsing the packaged sources (comments never count), not by grep. They must
be exactly four known lines in `main.js`; a read appended to one of them, `process["env"]`, or
`const { env } = process` (or via `globalThis`/`global`) is a different line or shape and fails. The gate still
never starts the artifact; the one thing it loads is the packaged `test-mode.js` / `argv-policy.js` (pure `node:fs`/`node:path`)
into a throwaway node process. This replaced a grep that flagged the
word in a comment in `argv-policy.js` and failed the Verify-artifacts job on `main` (workflow run
40829280033); the earlier exemption pattern was also loose (any line containing `unsafeSwitches(`), which
the exact-line match fixes. Mutation cases: a line or block comment mentioning `process.env` is accepted; a
real read appended to an exempt-looking line is refused.

Honest limits: this is a tripwire plus a gate, not a boundary. Chromium parses the debug-port switch
before any JavaScript runs, so a marker-less packaged build started with the switch still opens the
port until `main.js` exits 2 moments later; the marker only decides whether our own argv policy lets it
continue. Anyone who can write into the install tree (root) can already do anything. The gate proves the
shipped logic behaves as designed and that the marker is absent; it cannot prove what a user's machine
holds after install. **Follow-up**: drive the packaged build over `--remote-debugging-pipe` (no TCP port,
no marker, no env switch) from a parent process that owns the pipe.

Per package type, what stands between a local attacker and test mode:

| Artifact | Defence |
|---|---|
| AppImage, Flatpak | the launcher unsets `BENTO_TEST_HEADLESS` (gate: `check_unset` on `AppRun` / the Flatpak launcher), plus the marker |
| deb, rpm | **only the marker**: the launcher starts the binary directly with no env scrub. The install tree is root-owned, so an unprivileged user cannot create the marker; the gate asserts every package entry is `root:root` and nothing is group/world-writable or setuid (it can check the root ownership only on a real `.deb`/`.rpm`, not on an extracted `--tree`). A user who is root can already do anything. |

Windows: `hasTestMarker` needs POSIX owner and mode semantics, so on `win32` it **fails closed**: packaged
test mode is unavailable there, and no Windows packaged smoke test exists. A Windows-specific validation
(refuse reparse points, check the token, require the file to live under the install directory and to be
writable only by Administrators/SYSTEM) is the next step before any Windows packaged test mode; none of it
is implemented or verified.

Electron itself adds `--allow-file-access-from-files` to the argv it reports for a second instance
(found by the packaged smoke test; measured on Electron 45.1.0; the first launch's `process.argv` does
not have it), so that one switch is accepted in second-instance argv only; it cannot affect the running
process. Chromium reads its own switches before any script runs, so for the first launch this is a
fail-closed tripwire, not a filter.

Environment: `src/main.js` begins by exiting with code 2 if `ELECTRON_DISABLE_SANDBOX` or
`CHROME_DEVEL_SANDBOX` is set (the sandbox is already off by then, but no window or renderer is
created). `AppRun` and the Flatpak launcher additionally
`unset ELECTRON_DISABLE_SANDBOX CHROME_DEVEL_SANDBOX ELECTRON_EXTRA_LAUNCH_ARGS ELECTRON_ENABLE_LOGGING ELECTRON_RUN_AS_NODE NODE_OPTIONS`;
the gate requires every one of them in that line. Consequence: through `AppRun` or the Flatpak launcher the
sandbox variables never reach the app (the launch proceeds, sandboxed, with them removed); the
`main.js` refusal (exit 2) only fires when the binary is started directly, e.g.
`squashfs-root/bentopdf-native` or a deb/rpm entry. Verified separately for both paths. deb/rpm entries start the binary directly; there
the fuses cover RUN_AS_NODE and NODE_OPTIONS and the `main.js` refusal covers the sandbox variables;
`ELECTRON_EXTRA_LAUNCH_ARGS` and `ELECTRON_ENABLE_LOGGING` are the user's own environment (NOT
mitigated for deb/rpm). Windows are created with `sandbox: true` (asserted in
`test/security.test.js`) and the packaged smoke test checks the seccomp/no-new-privs/capability state
of every renderer.

An open-with grant records the file's device and inode (as bigint, so 64-bit NTFS file ids are not truncated), is opened with `O_NOFOLLOW` on POSIX (the path is
already resolved; win32 has no `O_NOFOLLOW`, see desktop-windows.md for its compensating checks), and `readFile` refuses it if the inode changed or the content no longer starts
with `%PDF-`. Dialog grants record dev/ino too.

"Open with" accepts only file arguments and `file://` URLs. A path is resolved with
`realpath`, must be a regular file of at most 512 MiB and must start with `%PDF-`
before a grant is issued, so a `x.pdf` symlink to a secret is refused.

## Payload file modes

electron-builder copies the modes of Electron's download. In the first build that made
**70** entries group/world-writable in the deb (`bentopdf-native`, `libffmpeg.so`,
`libvulkan.so.1`, `chrome_crashpad_handler` and `chrome-sandbox` at 0777; `.pak`, `.html`,
`.dat` and others at 0666), counted with `dpkg-deb -c` and equally in
`node_modules/electron/dist`. `desktop/tools/after-pack.js` now normalises the unpacked tree
before packing (`tools/normalise-modes.js`: directories 0755, files 0755 if any execute bit else
0644, `chrome-sandbox` 0755): **0** writable entries remain in the unpacked tree, the deb listing
(4,798 entries), the rpm listing (4,473) and the extracted AppImage. `verify-artifact.sh` fails on
any group/world-writable entry, any setuid/setgid entry (the setuid helper is created only by
the post-install script, never shipped), and a `chrome-sandbox` that is not exactly 0755 (absent in the Flatpak).

## Sandbox: what works, per format

No artifact, desktop entry or launcher contains `--no-sandbox` (asserted by the
gate; `smoke --no-sandbox` is a negative control that fails).

| Format | Mechanism | Proof |
|---|---|---|
| AppImage | Chromium's user-namespace sandbox. A squashfs mount is `nosuid` and not root-owned, so the setuid helper cannot work in an AppImage. | smoke test, host Fedora 44 / kernel 7.2: renderer `Seccomp: 2`, `NoNewPrivs: 1`, `CapEff: 0`, own user namespace |
| Flatpak | Electron2.BaseApp's zypak runs Chromium's sub-sandbox through the Flatpak portal | smoke test of the installed Flatpak (run with a test-only `--share=network` and `--filesystem=<tmp>`): renderer `Seccomp: 2`, `NoNewPrivs: 1`, `CapEff: 0` |
| deb / rpm | The payload ships `chrome-sandbox` as `root:root 0755` (not setuid; `verify-artifact.sh` fails on any setuid or group/world-writable payload entry), so no setuid helper exists between unpack and the post-install script. `packaging/linux/after-install.sh` then decides, fail-closed: user namespaces forbidden by sysctl, or the non-root probe (`setpriv --reuid=65534 ... unshare --user true`; as root `unshare` always succeeds) fails or a tool is missing: `chmod 4755` the helper. Only AppArmor restricts them (`apparmor_restrict_unprivileged_userns=1`, Ubuntu 23.10+): install the app-specific AppArmor profile (which grants `userns` to this binary) and keep 0755, falling back to setuid if the profile cannot load. Otherwise keep 0755. | The script logic is read from the built deb and rpm by the gate; the install paths themselves are NOT VERIFIED (installing needs root/layering here). Before this change every file in the payload was 0777/0666 (a root-run installer then made a world-writable binary's neighbour setuid): see "Payload file modes". |

**Where it cannot sandbox (AppImage):** hosts that forbid unprivileged user
namespaces (Ubuntu 23.10+/24.04 with `kernel.apparmor_restrict_unprivileged_userns=1`,
`kernel.unprivileged_userns_clone=0`, `user.max_user_namespaces=0`). electron-builder's
own AppRun silently adds `--no-sandbox` in that case; `packaging/harden-appimage.sh`
replaces it with `packaging/linux/AppRun`, which refuses to start. Exact
user-visible output (simulated by putting a failing `unshare` on `PATH`,
exit code 1; also shown with zenity/kdialog when present):

```
BentoPDF Native cannot start: Chromium's sandbox needs unprivileged user namespaces and this system does not allow them.

Typical causes: Ubuntu 23.10+/24.04 (AppArmor kernel.apparmor_restrict_unprivileged_userns=1), or kernel.unprivileged_userns_clone=0 / user.max_user_namespaces=0.

BentoPDF Native will not run without its sandbox.

What to do:
  - Immutable hosts (Bazzite, Silverblue, Kinoite): use the Flatpak build. Do not layer the .deb/.rpm just for this.
  - Other distributions: install the .deb/.rpm (its installer picks a working sandbox), or ask your administrator to allow user namespaces for this application.
  - Details: docs/desktop-linux.md in the source repository (see SOURCE.txt).
```

If `unshare` is missing the check is skipped and Chromium decides; with no
usable sandbox it aborts, never runs unsandboxed. Its own message
(reproduced with `--disable-namespace-sandbox` on the unpacked build):
`FATAL:setuid_sandbox_host.cc: The SUID sandbox helper binary was found, but is not configured correctly. Rather than run without sandboxing I'm aborting now.`

## Wayland / ozone

Desktop entries and the Flatpak wrapper pass `--ozone-platform-hint=auto`
(Wayland when the session is Wayland, X11 otherwise). Starting headless
(`--ozone-platform=headless`) is what is tested. On the development machine a
real Wayland window received no animation frames earlier (docs/m2-findings.md),
so visible-window behaviour on Wayland and X11 is NOT VERIFIED. The Wayland choice is a decision, not a result: no visible window was ever shown under Wayland or X11 for this package. The window
class / `app_id` is `io.github.bearyjd.BentoPDFNative` (`desktopName`),
matching `StartupWMClass`; the actual match in a live compositor is NOT VERIFIED.

## File association ("Open with")

All entries declare `MimeType=application/pdf`, `Categories=Office;Utility;`
and `%f` in the Exec line (electron-builder hardcodes `%U` for AppImage;
`harden-appimage.sh` rewrites it to `%f`; `file://` URLs are accepted anyway).

- Main process only: the command line (first launch) and the second-instance
  `argv` (plus macOS `open-file`) are filtered to `.pdf` paths (`src/open-file.js`),
  checked again on an open file handle (regular file, at most 512 MiB; no FIFO or
  device) and turned into an opaque grant token for the window. The renderer
  never supplies a path; it calls `bentoDesktop.takeOpenedFiles()` /
  `onFileOpened(cb)` and reads the file with `readFile(token)`, exactly like a
  file chosen in the native dialog. Tested by unit tests and by the smoke test
  (launch argument and a second instance forwarding its file).
- The bundled upstream pages do not consume these events yet; the viewer that
  does is M3. Making the default handler (`xdg-mime default`) is left to the
  desktop environment.
- Flatpak: files arrive through the document portal; the app has no
  `--filesystem` permission.

## Offline behaviour

The app makes no network requests of its own; a session hook cancels any
request outside `bento://app`, and the smoke test records zero external
resources. The Flatpak has no `--share=network` at all. Help > About states the
AGPL notice, no-warranty line and the source URL.

## Flatpak result

Assembled with `flatpak build-init` / `build-finish` / `build-export` by
`packaging/flatpak/build-flatpak.sh` (265 MB bundle; runtime 25.08 from flathub, user scope),
installed with `flatpak install --user --bundle` and smoke-tested headless: 12 of 12 checks
(the second-instance check is skipped for Flatpak: each `flatpak run` has its own sandbox
`/tmp`, so Chromium's singleton socket is not shared).

**Permissions, as installed** (`flatpak info --show-permissions io.github.bearyjd.BentoPDFNative`):

```
[Context]
shared=ipc;
sockets=wayland;fallback-x11;
devices=dri;
```

No plain `x11` socket, no network, no filesystem. Two facts found the hard way:
`flatpak build-finish` adds a plain `x11` socket by itself whenever `--socket=fallback-x11` is
given, and `--nosocket=x11` only removes it when it comes **after** `--socket=fallback-x11` (before it,
the final metadata still says `sockets=x11;wayland;fallback-x11;`: that was the earlier "x11 is
inherited from the BaseApp" result). The script and the manifest both put `--nosocket=x11` last;
the build tree metadata then reads `sockets=!x11;wayland;fallback-x11;` and the installed copy
drops the negation. `verify-artifact.sh` (run on the build directory) fails on a plain `x11`, on
network, on any filesystem or all-devices permission, and when the `!x11` is missing. The desktop
Exec is rewritten by Flatpak to forward `%f` via the document portal.

**Not "Flathub-style".** `packaging/flatpak/app.yml.in` is a declarative manifest rendered by the
build script, but `flatpak-builder --user --disable-rofiles-fuse` did not build it on the
development host. Exact error, in the first build command: `bwrap: Can't bind mount /etc/resolv.conf
on /etc/resolv.conf: Unable to mount source on destination: No such file or directory` (the agent
sandbox the build ran in; it may well work on a normal desktop). So the manifest path is NOT
VERIFIED, nothing here is submitted to Flathub, and the Flatpak is not built or gated in CI.
Installing from flathub into the user installation needed a throw-away private D-Bus socket as
`DBUS_SYSTEM_BUS_ADDRESS` (the agent sandbox has no system bus; flatpak queries it for parental
controls). Not needed on a normal desktop.

## Gate integrity

`packaging/test-verify-artifact.sh` extracts a deb, rpm, AppImage and the Flatpak build tree, then
for each of ~170 mutations makes a copy, breaks one thing and asserts that `verify-artifact.sh`
fails (after a positive control that the unmodified trees pass): missing/empty licence files, NOTICE
or SOURCE.txt; wrong SOURCE.txt commit, dirty flag, repository URL, tag line; a flipped fuse;
`--no-sandbox` in AppRun or a desktop Exec; 0777/0666/group-writable files and directories; setuid
and setgid files; a setuid or missing `chrome-sandbox`; dropped About/AGPL/source-offer strings; a
re-enabled `BENTO_*` override; `process.env` read elsewhere; argv policy or magic-byte check removed; a shortened `unset` list in AppRun or the Flatpak launcher; the `main.js` sandbox-env refusal removed; a
forbidden flag inside the asar; no `.desktop` file at all (empty glob); missing asar, bundle index or
executable; weakened post-install script; Flatpak x11/network/filesystem permissions; `--release`
on an unresolved NOTICE. Missing or empty inputs fail, never skip. CI runs it with `--no-flatpak`.

## Release hygiene (AGPL obligations)

Every artifact contains, checked by `verify-artifact.sh`: Electron's
`LICENSE.electron.txt`, `LICENSES.chromium.html`, our `LICENSE`, `NOTICE`, and
`SOURCE.txt` (repository URL, commit, `git describe`, release tag, branch and PR,
upstream tag and commit from `UPSTREAM_VERSION`/`UPSTREAM_COMMIT`, Electron version,
sha256 of the electron binary and of the Electron download zip, build date); the bundle
carries its own `resources/dist/SOURCE.txt`. The gate fails when SOURCE.txt names a
different commit than the checkout (a stale build) or says `dirty=yes`.

**Corresponding source of a release is the tag commit on main.** Pull requests here are
squash-merged, so a commit that exists only on a PR branch (such as the one named in the
SOURCE.txt of a pre-merge build) can disappear. Releases are built only from a tagged
commit on main, never from a PR branch. The workflow enforces it for tag builds: `HEAD`
must equal the tag's commit and the tag must be reachable from `main`; tag builds also
run `verify-artifact.sh --release` (release tag recorded, clean tree, zero unresolved NOTICE lines).
Non-tag builds still upload artifacts, but the artifact name and job summary say
`NOT FOR RELEASE` with the number of unresolved NOTICE lines (`packaging/check-notice.sh`).
Whoever distributes an artifact must offer the corresponding source; the About dialog links it.

Branding and trademark: the AGPL grants no trademark rights. This is an **unofficial**
build of BentoPDF; whether using the name "BentoPDF" in the product name is acceptable to
the upstream authors is NOT VERIFIED, and a rename is recommended (below). The application
icon is a neutral, self-made document glyph (`packaging/icons/icon.svg`, rendered by
`packaging/icons/render-icons.sh`); no upstream logo is used in the icon, desktop entries
or AppStream metadata. The bundled upstream pages still contain upstream branding.

## Renaming

Everything that carries the product name, app id, executable name, window class or
source URL is derived from **one file: `desktop/brand.json`** (`productName`, `appId`,
`executableName`, `iconPng`, `summary`, `sourceUrl`, `upstreamUrl`). Values are validated by strict
patterns (`desktop/tools/brand-check.js`: no quotes, `$`, backticks, `&`, `<`, newlines; https URLs only)
in `render-template.js` and `test/brand.test.js`, and are XML-escaped into the metainfo. To rename:

1. Edit `desktop/brand.json`.
2. Rebuild (`scripts/package-linux.sh`, `packaging/flatpak/build-flatpak.sh`).

`desktop/electron-builder.config.js` feeds `desktopName` into the packaged `package.json` (the window
class / Wayland `app_id`), and `test/brand.test.js` fails if `package.json` grows its own `desktopName`.

That covers `productName`, `appId`, the `.desktop` name and `Name=`, the WM class / Wayland
`app_id` (`StartupWMClass`), the metainfo `<id>`, the Flatpak id and its files, the executable
(and `AppRun`, launcher, the deb/rpm package name), the About text and the source link. The icon file path is in brand.json too (`iconPng`); to change the artwork replace
`packaging/icons/icon.svg` and run `render-icons.sh`. Not derived: the prose in `NOTICE`/docs, and
the `bearyjd` developer name in the metainfo.

## What the build tooling touched on the builder host

Nothing was installed system-wide and nothing was layered. Side effects of building here:

- **User-scope Flatpak installs** created by building the Flatpak (`~/.local/share/flatpak`):
  `org.freedesktop.Platform//25.08`, `org.freedesktop.Sdk//25.08`,
  `org.electronjs.Electron2.BaseApp//25.08`, and the test install of the app itself.
  Cleanup: `flatpak uninstall --user io.github.bearyjd.BentoPDFNative org.electronjs.Electron2.BaseApp//25.08 org.freedesktop.Sdk//25.08 org.freedesktop.Platform//25.08`
  (the runtime/SDK may be used by other apps: `flatpak list --user --runtime` first), then
  `flatpak uninstall --user --unused`. A throw-away `bentopdfnative*-origin` remote may exist: `flatpak remotes --user`, `flatpak remote-delete --user <name>`.
- **`libxcrypt-compat` borrowed into a scratch directory** (downloaded with `dnf download`, unpacked
  with `rpm2cpio | cpio`, never installed) and put on `LD_LIBRARY_PATH` only for the
  `scripts/package-linux.sh` run, because electron-builder's bundled `fpm` needs `libcrypt.so.1`.
  Cleanup: delete that scratch directory; nothing else refers to it.
- **Caches in `$HOME`**: `~/.cache/electron` (Electron download), `~/.cache/electron-builder`
  (fpm, appimage tools, mksquashfs), `desktop/node_modules`. Cleanup: remove those directories.
- **Repository build outputs** (git-ignored): `dist/`, `desktop/release/`, `packaging/generated/`,
  `packaging/flatpak/.build/`.
